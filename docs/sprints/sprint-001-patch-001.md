# Sprint 001 Patch 001 — Plannerが必要時にgrillingを呼ぶ

- Type: patch
- Risk: standard
- Base Sprint: sprint-001

## 目的と前提

Plannerが契約作成前にgrillingの必要性を判断し、重要な未決事項があれば遠慮せず利用する。
明確な依頼には余分なヒアリングを挟まず、深掘りしたユーザーの意思を仕様・契約へつなぐ。

- ユーザーは必要時だけのSkill利用、Plannerによる範囲・保存先の判断、独立Griller roleを設けない方針を承認済み。
- 判断に迷う場合のorchestratorへの相談を取り入れる。相談を全件必須の承認待ちにはしない。
- この方針について再ヒアリングせず実装する。
- 既存の固有grilling行動回帰がないため、microではなく通常Patchとする。

## Scope

1. `mattpocock/skills`のgrillingを、出典・revision・licenseを伴う独立した同梱Skillとして取り込む。
2. upstreamのヒアリング本体を尊重し、Harnessへの接続指示と区別する。
3. Planner、loopの呼び出し・fallback、入口・テンプレート・現在形の関連案内を以下の判断へ揃える。
4. 新しい行動を守るため、既存の回帰チェックに必要な確認を加える。

## 受け入れ基準

### AC-01 必要性を先に判断する

Plannerは依頼・会話の既決事項・関連仕様を読んでから、grillingを呼ぶか判断する。
目的・期待挙動・範囲が明確なら省略し、孤立した不足なら通常の短い確認で補う。
完成形を左右する曖昧さ、回答に依存する判断の連鎖、要望の矛盾が残れば、手間への遠慮で省かずgrillingを呼ぶ。
新規開発・Patchという種別や質問数だけを要否の決定条件にしない。

### AC-02 深掘りは同梱grillingを利用する

必要時にはPlannerが実際に同梱Skillを読み、その質問・調査・認識合わせの手順を使う。
先の回答に依存する質問を先回りして確定せず、回答後に次の問いを組み直す。
固定の3問制限や別の重複ヒアリング手順を残さず、host UIの件数制限は全体の上限と扱わない。
upstream本文の出典・固定revision・licenseが配布物内で追跡できる。

### AC-03 Plannerの責務とユーザーの意思を保つ

ユーザーの明示指示を優先し、指定がなければPlannerが深掘りの対象範囲と既存ファイル規約に沿う保存先を決める。
既決事項を聞き直さず、調べられる事実は調べ、ユーザーにしか決められない判断を問う。
合意した内容・理由・具体例を必要な仕様とSprint契約の受け入れ基準へ反映する。
未依頼機能やAI活用は提案できるが、合意または明示委任なくscopeへ加えず、機能数・Sprint数の目標を強制しない。
明示委任された範囲ではPlannerが前提を記録して進める。無回答を委任とは扱わない。
実装手段の詳細はGeneratorの責務のままとする。

### AC-04 迷った場合の相談とhost fallback

重要な未決事項を残して省略してよいか、深掘り範囲が権限を越えるか迷う場合、Plannerは
未決事項と推奨する進め方をorchestratorへ伝える。orchestratorは既存の承認・文脈を確認するか
ユーザーへの質問を中継し、ユーザーの意思を代わりに作らない。
利用可能なhost-native質問UIを優先し、使えなければ通常の短い質問、子roleから質問できなければ
親への中継で継続する。Skill専用呼び出しがなければ同梱ファイルを読んで使える。
no-subagent fallbackでも同じ必要性判断と責務を維持する。

### AC-05 現行案内の整合と回帰

現行配布面の「最大3問」「無条件に質問ループを開始／省略不可」等を上記方針へ揃える。
過去の記録や既存ツールAPIの実際の件数制約は改変しない。
既存positioning・loop-rule・runtime-config回帰を通過し、runtime routing、初期化のno-overwrite、
roleの正本所有を維持する。公開versionと導入済みcacheを変更しない。

## Non-scope

- 独立Griller role、新しい設定キー、別のヒアリング管理ファイルや評価基盤
- 次Sprintの実装、runtime/model routing変更、ユーザー所有設定や導入済みpluginの更新
- release、version bump、Marketplace公開

## 検証スコープと必須シナリオ（着手時に固定）

対象は画面を持たない配布Skill / roleの行動と配布整合。実際の同梱指示を読んだ独立roleで次を確認する。

1. 明確な限定変更はgrillingを省略し、範囲・保存先を判断する。
2. 孤立した不足は短い通常確認とし、不必要な全面ヒアリングへ広げない。
3. 重大な曖昧さ・判断の依存関係・矛盾がある依頼はgrillingを選び、回答後の次の質問へつなぐ。
4. 省略または範囲判断に迷う場合は根拠付きでorchestratorへ相談し、重要判断を代行しない。
5. 明示委任・既決事項を尊重し、無回答は委任に変換しない。追加機能を勝手に契約へ入れない。
6. Skill専用呼び出し／質問UI／subagentがない場合の案内が、読取・通常質問・親中継を通じて同じ判断を保つ。

証拠形式と採点は[Evaluation Rubric](../spec/rubric.md)のPatch専用節を使う。
行動確認は少数の記録で複数シナリオを満たしてよく、形式の統一や新しい収集基盤は不要。
Generatorは変更・確認結果・限界をprogressへ、Evaluatorは独立確認と各findingのtarget classをfeedbackへ記録する。
