# 評価と証跡

評価前にEvaluatorとオーケストレーターが読む。再評価は前回の見送り記録と変更した対象・依存物に関係する節を確認する。

## findingの選別と収束

この規則は小変更・通常機能・Sprint、および両hostで共通。Evaluator、外部レビュアー、
オーケストレーター自身の気づき、貼り付けられたレビューを問わず、修正指示や合否判定の前に適用する。

各findingに発生条件・根拠・頻度F（0〜10）・影響I（1〜10）・対象区分 `product` / `verification-infra`・
扱い（修正/見送り/要判断）を付ける。対象区分が不明ならproductとする。
Fは対象製品の想定利用内の見積りでよく、統計・監視基盤を新設しない。具体的な発生条件を示せなければF=0。

追加の品質findingは **`F×I >= 20 OR (F >= 1 AND I >= 8)`** を修正対象とし、未満は見送る。
既定ではF=2/I=9・F=4/I=5は修正、F=2/I=7・条件不明F=0/I=9は見送りとなる。
数値20/8はplugin既定であり、必要なrepoだけ既存 `docs/spec/rubric.md` で明示的に上書きできる。
通常機能や小変更にrubric作成を強制せず、進行中の無断厳格化はしない（[厳格化ゲート](scope.md)）。

次は頻度閾値の対象外として対処し、受け入れ評価にも含める。

- 明示された受け入れ条件の未達。
- 今回の変更による実証された回帰。変更前後の実挙動や既存の有効なテストなどで変更との関係を示す。
- セキュリティ・認証/権限・個人情報/顧客データ漏えい・データ消失/破損・課金/請求の具体的欠陥。
  欠陥と影響経路を示し、カテゴリ名だけで新たな設計や検証基盤を要求しない。

「動作安定性」「回帰なし」という一般的見出しで低優先findingを必須修正へ変換しない。
既存の軽微な不具合や仮説を今回の回帰と呼ばない。利用者の明示的な修正依頼は数値だけで拒否しない。
根拠のない一般findingはF=0で見送り、重大例外や承認に関わる本当の未決だけをまとめて確認する。

見送りfindingだけを理由にFAIL/incompleteにせず、次の間接的な差戻しも禁止する。

1. 見送りを理由に採点を下げ、合格閾値を下回らせる。
2. 必須検査でも再現済み欠陥でもない仮説を「未確認」と呼び、完了を止める。
3. 同じ見送りを `spec-issue` / `verification-scope-issue` に付け替えて往復を再開する。

FAILには未達の受け入れ条件または選別後の修正対象findingを対応させる。
実行できなかった必須検証は見送り仮説と区別し、未確認として記録してPASSにせず、[限定修理・検証スコープガード](scope.md)へ進む。
対象区分や修正先の分類はこの選別後に使い、選別を迂回する根拠にしない。

見送りはSprintならfeedbackの「残課題」、通常機能・小変更なら既存作業記録と完了報告に残す。
再評価では前回記録を参照し、全文複写・項目ごとのIssueや新台帳の自動作成をしない。
関連コード・設定・依存物の変更、新しい具体的事実、利用者の明示再評価がある場合だけ再開し、何が変わったかを書く。
言い換えや点数変更だけは新事実ではなく、未変更の見送りを再発行しない。

### ブラウザ検証面の優先順位
Evaluator はコードを読むだけで判断しない。CLI・API・pluginなど非UI製品はコマンドや入出力を実行して確かめる。UIの評価では次の優先順位で実物を操作する。

1. **Codex App:** Browser Use / `@Browser`。ローカル preview、クリック、フォーム入力、スクリーンショット、
   console/network 確認に使う。
2. **Claude Code Desktop App:** Preview pane / autoVerify。Claude ネイティブの embedded preview で
   dev server 起動、スクリーンショット、DOM inspection、クリック、フォーム入力を行う。
3. **Codex CLI / Claude Code CLI:** Playwright。既存の Playwright test があれば実行し、無ければ
   Playwright script / CLI で最低限の起動確認、スクリーンショット、フォーム操作、console error 確認を行う。
   ホストに Playwright MCP が既に設定されている場合はそれを使ってよいが、ハーネス側から常時起動はしない。
4. **例外:** Computer Use や実 Chrome は、ログイン済みブラウザ状態、ネイティブアプリ、GUI 専用操作が
   必要なときだけ使う。標準経路にはしない。
5. **Fallback:** どれも使えない場合は、build、HTTP 疎通、静的スクリーンショット、手動確認項目を
   対象の `docs/feedback/sprint-*.md` に明記する。

## 評価基準と閾値

閾値の正本は `docs/spec/rubric.md`（Planner がプロジェクト種別に応じて生成・更新する）。
Sprintで採点を使いrubric.md が無い場合だけ次の既定値を使う。

| 基準 | 既定閾値 | 不合格時 |
|------|---------|---------|
| 機能完全性 | 4/5 以上 | Generator に差し戻し |
| 動作安定性 | 4/5 以上 | Generator に差し戻し |
| デザイン性 | 3/5 以上 | Generator に差し戻し |
| 独自性 | 3/5 以上 | Generator に差し戻し |
| エラーハンドリング | 3/5 以上 | Generator に差し戻し |
| 回帰なし | 5/5 必須 | Generator に差し戻し |

**1つでも閾値を下回ればスプリント不合格。** 採点にも上のfinding選別を適用し、見送りだけで閾値を下回らせない。
このハードゲートの対象は、Sprint 着手時点で
契約・rubric に存在した基準に限る。ループ中に追加された基準の扱いは「受け入れ基準・rubric の
厳格化ゲート」に従い、当該 Sprint では参考スコア・改善提案とする。

小変更は独立Evaluatorを必須にしない。担当Agentが影響に必要な確認を行い結果を報告する。
通常機能では短い計画・受け入れ条件に対する独立確認で足り、6軸採点表やrubric新設は不要。
以下の既定採点表は、Sprintで採点を使いrubricが未作成のときだけ適用する。

**再評価の増分原則**: 評価した候補と関係する依存物を、commitと対象ファイルの差分、設定・実行環境の記録など既存手段で特定する。Evaluator自身が前回との実差分を確認し、変更面と影響する回帰だけを再実行する。範囲を絞る根拠と再利用したfeedbackを記録する。契約が全スイート実行を要求する場合は従う。
候補・依存物が同一で前回の実行証跡が十分なら再利用できる。無関係なdirtyは失効理由にせず、既存変更を戻さない。関連変更、不明な依存、確認不能な同一性があれば該当証跡を再取得する。Generatorの申告だけで同一と判断しない。
引き渡された必要な回帰チェックが実行不能・失敗のままなら「回帰なし」をPASSにせず、[限定修理または検証スコープガード](scope.md)へ進む。既存証跡再利用に新しいdigest/collector基盤を要求しない。

**合格の証跡（下限）**: 判定の根拠となる実行コマンドと結果、対象操作の入出力を feedback に必ず残す。UIでは実URL/DOM/ブラウザ操作の記録を残す。
UI・レスポンシブ・視覚品質を採点した場合はスクリーンショットも必須。証跡の無い合格は無効として扱い、
オーケストレーターは Evaluator に差し戻す。

**証拠の十分性（上限・safe harbor）**: rubric と契約に列挙された証拠形式を満たせば、その基準の合格に十分である。
Evaluator は契約・rubric に無い証拠形式（期限付き approval manifest、digest 固定、attestation、
検証面を跨ぐ統一証拠 schema など）を発明して合否条件にしない。選択した検証面が自然に生成できる証拠
（コマンド結果、実操作の記録、スクリーンショット、host 側の session 記録）で足り、証拠収集のための
新しい基盤・collector・schema の開発を合格条件にしない。より強い証拠が必要だと考えた場合は、
FAIL の理由にせず改善提案に書き、採否は厳格化ゲート（ユーザー承認）に委ねる。
実挙動の欠陥（product finding）は上の選別で修正対象となるものを証拠付きで不合格にできる。
証拠形式の列挙は「合格の証跡（下限）」を下回れない。列挙が下限より弱い場合は下限が優先する。
rubric・契約に証拠形式の列挙が無い場合は、下限に挙げた形式を safe harbor の列挙とみなす
（Planner は次の改訂時に証拠形式セクションを補う。下限の成文化は厳格化ゲートの対象外）。
また safe harbor が制限するのは合否条件・必須シナリオ・証拠形式の要求の拡大であり、
Evaluator が検証中に観察する範囲は制限しない。固定した検証対象の外で観察された実挙動の欠陥は、
product finding として記録できるが、修正・合否への扱いは上の選別に従う。

**ユーザー実機確認の採用**: ユーザーがチャットで明示的に宣言した実機確認は、オーケストレーターが
state.md へ記録した場合に限り、該当する受け入れ基準の証跡として採用できる。
記録には、日時、ユーザー宣言の引用、対象の受け入れ基準（包括的な宣言は基準単位に分解する）、
確認時点の候補・依存物（commitと関連差分など）を含める。対象基準に関係する候補・依存物が変更されたら証跡として
失効し、再確認または通常の Evaluator 証跡が必要になる。
Generator の自己申告は従来どおり証跡にならない。
