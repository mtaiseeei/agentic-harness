# 開発の進め方と文書

## FLOW-001 影響に応じた実行

小変更は影響範囲、可逆性、外部契約、データ、権限、失敗時影響で判断する。小さな挙動変更も対象で、
行数・画面数・既存自動テストの有無を硬い資格条件にしない。担当Agentが直接修正・必要検証して完了でき、
独立レビュー、micro契約、3役、3文書、専用Sprint開始を必須にしない。既存管理repoでも同じである。

通常機能は必要な短い計画を置き、完成時に実装者とは独立したレビューを行う。高リスク変更は既存の
実行前確認、承認境界、実行後検証を維持する。大きく曖昧な開発では必要な設計文書と意味のある単位を使う。
承認済み範囲の可逆な実装判断・修理を自律的に進め、同じ承認を聞き直さない。沈黙は承認にならない。

## DOC-001 現在状態と条件付き読取

AGENTS / CLAUDEは短い常設境界、基本コマンド、条件付き入口を置く。stateの正本は一つとし、
現在の目的、進行中作業、未解決事項、次の一手、有効な承認・制約、必要仕様への参照、
直近検証の対象版と証拠参照を保持する。実装済み・検証済み・配備済みを区別する。

stateは現在状態を更新し、過去詳細を履歴へ保持する。50行程度 / 数KBは初期目安で停止ゲートではない。
巨大な一行を見逃さず、短縮のため未解決事項や有効な承認・制約を落とさない。
state / NEXT_SESSION / PROJECTへ同じ現在状態の正本を増やさない。

開始・再開は現在状態→該当仕様 / コード→矛盾や理由が必要な場合だけ関連履歴の順。
既存repoの正本と規約を利用し、CONTEXT.mdや定型文書群を無条件追加しない。
領域別の現行仕様を必要な分だけ読み、索引を短くする。分割後も全fileを毎回読む指示は置かない。
重要判断の確定時は該当仕様と判断履歴を整合更新し、置換済み判断を識別できるようにする。

## ASK-001 資料を使う質問

既存資料から既知事項・今回の変更・未決事項を把握し、推奨案を添えて重要な質問だけ行う。
今回を進めるため利用者が決める必要のある事項が解決した時点で質問を終了し、確定内容を既存仕様へ反映する。
全設計分岐の訪問、既決事項の聞き直し、委任済み実装詳細の確認を必須にしない。
単発修正にgrillingは必須ではない。明示的な深いgrillingは引き続き利用できる。

記事のgrill-with-docsは設計参考であり、同梱mattpocock/skills grillingと同一実装と説明しない。
外部実装を取り込む場合はsource / license / provenanceを検証する。

## MIG-001 既存repoの保守移行

plugin更新とrepo guidance移行を区別し、安全にpreviewして変更範囲を確認できる実行手段を配布する。
初期化はno-overwriteを維持する。保守移行では承認済み対象に限定して更新し、元履歴、独自規則、dirtyを保持する。
既存正本の利用、参照切れ、未解決事項の脱落、対象範囲にある旧指示の残存を必要な範囲で確認する。
機械的に安全と判断できない箇所は残して報告し、黙って削除・要約・更新完了扱いにしない。
preview後に対象が変化した場合も、確認していない内容を古いpreviewで上書きしない。

## REV-001 レビューの収束（v0.6.1 / #12）

詳細な判断は配布正本 `plugins/harness/skills/harness-loop/references/evaluation.md` に集約する。
findingは発生条件・根拠・頻度F（0〜10）・影響I（1〜10）・product / verification-infra・扱いを持つ。
追加品質findingの既定修正条件は `F×I >= 20 OR (F >= 1 AND I >= 8)`。条件不明はF=0とする。
明示受け入れ条件未達、今回の変更による実証回帰、具体的なセキュリティ・権限・情報漏えい・データ破損消失・
課金請求の欠陥は閾値対象外として対処する。カテゴリ名や一般的な安定性だけで例外へ変換しない。
見送りだけを減点・仮説の未確認扱い・分類変更で不合格へ戻さず、必須検証の未実行はPASSにしない。
再開は関連変更・新しい具体的事実・利用者の明示再評価に限り、その差分を記す。
残課題は既存feedback / 作業記録と完了報告へ置き、前回を参照する。新台帳や個別Issueを自動作成しない。
既存rubricによる明示上書きは可能だが、新規作成の強制・進行中の無断厳格化はしない。
外部レビューや親の発見も同じ選別を行い、利用者の明示修正依頼を閾値だけで拒否しない。
Generatorは選別後の修正対象を扱い、将来用の抽象化や依頼外の稀なケースを増やさない。

## DOC-002 現在地の置換更新（v0.6.1 / #13）

stateは固定見出し「現在地」の1欄を現行値の正本とし、再開・引き渡し時に確認、完了・割込み復帰時に更新する。
日報・検証出力をprepend / appendせず既存progress / feedback / reportへ置き、stateには参照を残す。
旧Current ID等は移管済み履歴として明示し、現行値へ復活させない。目安を満たすための巨大1行化も認めない。
承認・制約・保留・元目的・復帰先・対象版/証拠・実装/検証/配備の違い・counterを保持し、推測拡張やリセットをしない。
巨大旧stateは先頭200行だけで判断せず、今回に関わる有効事項を検索し既存upgradeのpreview / applyと原文退避を使う。
レビュー済みの履歴範囲は行範囲/hash/理由を明示し、原文archiveへの参照と有効事項のexact preserveを伴って退避できる。
範囲外の保護行・明示preserve・liveリンク制約は維持し、履歴の意味をCLIが判断しない。原文bytesを適用後と再適用時に照合する。
意味を確認できず整理できなければ、原文を同じstate内に履歴として保持し、短い現在地欄を置換更新する。
整理未完了を明記して別の保守作業へ残し、承認済みの独立作業を継続する。承認不明な高リスク操作だけ留保する。
全履歴整合、archive全文読込、新しい停止閾値・整理エンジン・監視ループを標準経路にしない。

## FLOW-002 割込みから本題へ復帰（v0.6.1 / #14）

現在地に元依頼の目的・完了条件・現在作業を保持する。割込み時だけ理由・終了条件・具体的な復帰先を追加する。
小問題への「直して」はその修理の承認であり元依頼の取消ではない。明確な中止・置換指示は優先する。
割込みは本題の阻害、今回の回帰、具体的重大欠陥、利用者が明示優先した作業に限る。閾値だけで無関係な作業へ移らない。
修理中の無関係な軽微問題は残課題へ置く。修理と必要確認後は前提変化を確認し、現在地を更新して承認済み本題へ自動復帰する。
復帰の再承認や元作業の全レビューを要求しない。子roleへの依頼・戻り値にも親目的、担当範囲、終了条件、復帰先を含める。
子の完了を全体完了としない。外部入力待ちは阻害条件と独立作業を示し、新情報のない確認・修理を繰り返さない。

## DIST-001 配布と適用の区別（v0.6.1 / #15）

両hostの入口・template・guidanceは詳細正本への短い実行導線を持つ。評価前、開始/復帰時、再開/引き渡し時に読む。
既存upgradeで衝突指示を確認し独自規則・有効承認・dirtyを保護する。機械検出だけで全矛盾解消を断定しない。
global `review-convergence:v1` は非Harness環境用の10行以内のfallback案を案内するが、個人設定を自動変更しない。
対象repoで新規則の実読込と整合を確認するまでは既存globalを残す。
source公開、installed版、fresh sessionの実読込path/内容、消費repo適用を別々に確認・報告する。
小変更の直接完了を維持し、全作業へ3役・Sprint・文書群を再強制しない。
